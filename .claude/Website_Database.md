## Tables Used by the Website

### `waitlist`

The only table the website writes to. Stores email addresses from the landing page signup form.

#### Schema (live — verified April 2026)

```sql
CREATE TABLE waitlist (
  id          uuid      DEFAULT gen_random_uuid() PRIMARY KEY,
  email       text      NOT NULL UNIQUE,
  source      text      DEFAULT 'website',
  created_at  timestamp DEFAULT now()
);
```

#### Columns

| Column | Type | Nullable | Default | Notes |
|--------|------|----------|---------|-------|
| `id` | uuid | NO | gen_random_uuid() | Primary key — auto-generated |
| `email` | text | NO | — | UNIQUE constraint — duplicates rejected with error code 23505 |
| `source` | text | YES | 'website' | Always 'website' from the landing page form |
| `created_at` | timestamp | YES | now() | Auto-set on insert — not sent by the form |

#### Constraints

| Constraint | Type | Details |
|-----------|------|---------|
| `waitlist_pkey` | PRIMARY KEY | id |
| `waitlist_email_key` | UNIQUE | email — duplicate inserts return error code 23505 |

#### RLS (Row Level Security)

```sql
ALTER TABLE waitlist ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Allow insert"
  ON waitlist
  FOR INSERT
  WITH CHECK (true);
```

- **RLS is ENABLED** — all access goes through policies
- **Public can INSERT** — no auth required (anon key sufficient)
- **Public CANNOT SELECT, UPDATE or DELETE** — no policy exists for these operations
- **Service role bypasses RLS** — never expose service_role key on frontend

#### How the website writes to this table

```javascript
// js/main.js
const res = await fetch(`${SUPABASE_URL}/rest/v1/waitlist`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'apikey': SUPABASE_ANON_KEY,
    'Authorization': `Bearer ${SUPABASE_ANON_KEY}`,
    'Prefer': 'return=minimal'
  },
  body: JSON.stringify({ email: userEmail, source: 'website' })
})
```

Only `email` and `source` are sent. `id` and `created_at` are auto-generated by Supabase.

#### Error handling

| HTTP Status | Supabase Code | Meaning | Website response |
|------------|--------------|---------|-----------------|
| 201 | — | Insert successful | Success message (cyan) |
| 409 | 23505 | Duplicate email | Friendly message (orange) |
| Other | — | Network/server error | Error message (red) |

## Supabase Webhook Configuration

The `waitlist` table has one active webhook:

| Field | Value |
|-------|-------|
| Name | `waitlist_new_signup` |
| Table | `waitlist` |
| Event | INSERT only |
| Type | HTTP Request |
| Method | POST |
| URL | Make.com webhook URL (see Make.com scenario "Fathom Blue Waitlist") |

The webhook fires on every successful INSERT and sends the full new row as JSON to Make.com.

**Payload received by Make.com:**
```json
{
  "type": "INSERT",
  "table": "waitlist",
  "record": {
    "id": "uuid",
    "email": "user@example.com",
    "source": "website",
    "created_at": "2026-04-16T..."
  },
  "schema": "public"
}
```

Make.com accesses the email via `{{1.record.email}}` in the scenario modules.

## How to Verify Live Schema

Before any brief touching the `waitlist` table, run this in Supabase SQL Editor:

```sql
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'waitlist'
ORDER BY ordinal_position;
```

And verify constraints:
```sql
SELECT conname, contype, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'public.waitlist'::regclass;
```

## Supabase Access Keys — Website

| Key | Location | Permission | Notes |
|-----|----------|-----------|-------|
| Anon public key | js/main.js | Insert only (via RLS) | Safe on frontend |
| Service role key | NOT on website | Full bypass of RLS | Never use on frontend |

The anon key is a JWT starting with `eyJ...`. It is safe to have in frontend code when RLS is correctly configured with insert-only policy. Anyone who extracts the key from the browser can only insert rows into the waitlist table — they cannot read, update or delete.
